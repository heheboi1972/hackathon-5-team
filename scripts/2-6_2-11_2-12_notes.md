## 2-6. watsonx 임베딩 래퍼 + embed_sessions 잡

**확인된 것**: `ai_service.py`의 `embed_documents`/`embed_query`(passage:/query: 접두사 자동 적용)는 이미 구현되어 있었음 — 2-6의 "임베딩 래퍼" 부분은 새로 만들 필요 없었음. `jobs.py`(2-0, 윤석)도 이미 구현 완료 — SKIP LOCKED 워커 루프, 재시작 시 running→queued 복구까지 있음. `apply_upload()`(postgres_service.py)도 이미 `embed_sessions` 잡 INSERT까지 하고 있었음.

**이번에 새로 채운 것**: `api/app/services/embed_sessions.py` (신규 파일)
- `chunk_session_text()`: 세션 메시지를 "A: ...\nB: ..." 형식 청크로 나누는 순수 함수. 한 청크 최대 700자(e5-large TRUNCATE_INPUT_TOKENS=512 토큰 기준 보수적 추정). 사진 등 text가 아닌 메시지는 제외, 세션에 text가 하나도 없으면 빈 리스트 반환(임베딩 대상에서 자연히 빠짐).
- `build_points()`: 임베딩 벡터 → Qdrant point 리스트. id는 `{couple_id}:{session_id}:{chunk_idx}`를 uuid5로 해싱해서 사용 (아래 "확인 필요" 참고).
- `run_embed_sessions_job()`: JobService 핸들러. 세션별로 청킹→임베딩→Qdrant upsert→진행률 갱신. 세션 하나 실패해도 잡 전체를 죽이지 않음(failed 카운트만 증가).
- `container.py`에 `jobs.register("embed_sessions", ...)` 추가로 등록 완료.
- `postgres_service.py`에 `get_messages_for_embedding()` 메서드 추가 (session_id 포함해서 메시지 조회 — 기존 `get_stored_messages()`엔 session_id가 없었음).
- `qdrant_service.py`에 `upsert_sessions()` 메서드 추가 — 원래 TODO(윤석)였는데, embed_sessions 잡이 실제로 동작하려면 필요해서 이번에 같이 채움. **윤석 검수 필요.**

**⚠️ 확인·검수가 필요한 부분 (실제 Postgres/Qdrant 인프라에서 못 돌려봄)**:
1. **Qdrant point id 형식**: TASKS.md/기존 주석엔 point id를 `{session_id}:{chunk_idx}` 문자열로 쓰라고 되어 있는데, Qdrant는 point id로 부호없는 정수 또는 UUID 형식만 허용하고 임의 문자열은 거부하는 것으로 알고 있음. 그래서 이번엔 그 키를 `uuid5`로 해싱해서 사용하도록 바꿨음(같은 입력 → 항상 같은 UUID라서 재업로드 시 멱등 upsert 속성은 유지됨). 원래 문자열은 `payload.point_key`에 남겨둠. **윤석이 실제 Qdrant에 붙여보면서 이 부분이 맞는지 한번 확인해줘야 함.**
2. 이 파일 전체가 실 Postgres/Qdrant/watsonx 없이 로직만 검증됨 (`chunk_session_text`/`build_points`는 순수 함수라 로컬에서 여러 케이스로 검증 완료, `api/tests/test_embed_sessions.py`에 있음). `run_embed_sessions_job()`은 인프라 붙은 뒤 스모크 테스트 필요.

## 2-11. 제안 템플릿 풀

`data/knowledge/templates.json`에 26개 작성 (지표 5개 × 방향 2개 = 10 조합, 조합당 2~3개). `question_rate`, `message_length_median`, `reply_gap_median_min`은 조합당 3개, `resume_delay_median_min`, `session_length_median`은 조합당 2개.

모든 템플릿은 `banned_patterns.txt`의 8개 카테고리 정규식을 코드로 직접 돌려서 하나도 안 걸리는 것 확인함 (인물 지목·비교·수치·등급·가치판단·원인단정·명령당위·관계판정 전부 회피). 주어는 전부 "우리", 종결은 권유형("~해보면 어떨까요" 류).

**참고로 발견한 것**: 1-7에서 만든 지식 문서 10개가 지표 4개(question_rate, message_length_median, reply_gap_median_min, resume_delay_median_min)만 다뤘었는데, `metrics.py` 확인해보니 실제로는 `session_length_median`까지 5개가 맞는 지표였음(A2 이슈로 `initiation_ratio`가 빠진 자리). 그래서 `data/knowledge/interpretations/`에 `session_length_median_up.md`, `session_length_median_down.md` 2개를 추가로 채워서 1-7의 지표 커버리지도 5개로 맞춰놨음.

## 2-12. 에이전트 지시문 + 검수 규칙표

`interpret.md`는 오늘 오전(1-V4)에 이미 끝나 있었음 — 그래서 이번엔 나머지 3개(select/suggest/safety)만 작성.

- `select.md`: 계약(입력 trend_candidates+outlier_candidates+notes/events, 최대 3개 후보 출력)을 지키는 지시문 작성. "메모(C1)" — 이 에이전트 자체가 나중에 코드로 대체될 수 있다는 계약 상단 메모는 지시문에도 "알려진 한계"로 그대로 남겨둠.
- `suggest.md`: 2-11 템플릿 풀을 참조하는 지시문. 템플릿 밖 자유 생성 금지, 1~2개만 고르는 규칙 반영.
- `safety.md`: 지시문 + **검수 규칙표**(banned_patterns.txt 8개 카테고리 × 재작성 방향 × 예시). 점수·등급, 관계 판정 카테고리는 "재작성 대신 삭제"로 명시 — 다듬어도 여전히 위험하게 읽히는 카테고리라서.

**미완료로 남긴 것**: 이 3개 지시문은 오늘 오전 interpret.md/lexicon.md처럼 Prompt Lab에서 실제로 테스트해보진 못했음(시간상). select/suggest는 로직이 명확해서(고정된 후보 중 고르기) 리스크가 낮다고 보는데, safety.md의 "재작성" 부분은 gpt-oss가 실제로 규칙표대로 잘 다듬는지 몇 개 케이스로 확인해보는 게 좋을 것 같음 — 여유 될 때 1-V4/1-8 때처럼 골든셋 3~5개로 검증 권장.
